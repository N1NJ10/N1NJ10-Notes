The zero-extend trap

Writing a 32-bit register clears the top 32 bits to zero. Writing a 16-bit or 8-bit register leaves the upper bits untouched.

; rax = 0xFFFFFFFFFFFFFFFF
mov eax, 1   ; rax = 0x0000000000000001  <- top half wiped
mov ax,  1   ; rax = 0xFFFFFFFFFFFF0001  <- top 48 bits survive
mov al,  1   ; rax = 0xFFFFFFFFFFFFFF01  <- top 56 bits survive

This is why xor eax, eax is the idiomatic way to zero rax: it is shorter than mov rax, 0 and clears all 64 bits anyway.

Where the high byte went

ah bh ch dh exist only for the four legacy registers, and only in instructions that need no REX prefix.

  • You cannot mix ah with sil, dil, spl, bpl, or any r8–r15 in the same instruction — the encoding has no room for both.
  • sil dil spl bpl only became addressable in 64-bit mode; in 32-bit code the low byte of esi has no name.
  • Assemblers accept r8l as a synonym for r8b.

Who owns what

Calling conventions

Same 16 registers, two incompatible sets of rules. Linux and macOS use System V; Windows uses its own. Callee-saved means: if your function touches it, push it in the prologue and pop it in the epilogue. Volatile means any call you make may destroy it.

Argument order, memorised

System V: rdi rsi rdx rcx r8 r9 — then right-to-left on the stack.
Mnemonic: Diane's Silk Dress Cost $8 9.

Windows: rcx rdx r8 r9 — then on the stack, above the shadow space.

Floats go in xmm0+ in both. On Windows the integer and float slots are shared by position: a double as arg 2 uses xmm1 and skips rdx.

Variadic functions (printf)

On System V, calling a ... function requires al = the number of vector registers used. If you pass no floats, it must still be set:

lea  rdi, [rel fmt]
mov  rsi, 42
xor  eax, eax      ; al = 0 floats
call printf wrt ..plt

Forgetting xor eax, eax is a classic segfault in printf.

The dividing line

What lives in the CPU, what lives in RAM

Assembly has no variables in the sense you know from C. It has registers, which are named, and memory, which is addressed. Almost every bug in early assembly comes from confusing the two.

CPU side — registers

  • 16 GPRs + 16 XMM. That's the whole workspace. Run out and you spill to memory.
  • Named, not addressed. rax has no address. You cannot take a pointer to it.
  • Sub-latency. Reading a register is free; reading RAM is 4–300 cycles depending on cache.
  • Contents die at the next call unless the register is callee-saved.
  • Written as a bare name: mov rax, rbx.

RAM side — memory

  • Effectively unlimited, addressed by 64-bit pointers.
  • Everything with a label in .data, .bss, .rodata is here, plus the stack and the heap.
  • Persists across calls — that's what the stack frame is for.
  • Needs a size when the assembler cannot infer one: mov qword [rax], 1.
  • Written in brackets: mov rax, [rbx] means load from the address in rbx.

Moving between the two

Legal and illegal operand pairs

  • ✓mov rax, rbx register ← register
  • ✓mov rax, [rbx] register ← memory (a load)
  • ✓mov [rbx], rax memory ← register (a store)
  • ✓mov rax, 42 register ← immediate
  • ✓mov qword [rbx], 42 memory ← immediate, size required
  • ✗mov [rax], [rbx] memory ← memory never encodes. Use two instructions via a register.
  • ✗mov rax, [rbx] with mismatched widths both operands must be the same size — use movzx/movsx to widen.
  • ✗mov rax, 0x1122334455667788 into memory 64-bit immediates only go into registers; mov r64, imm64 is fine, mov [mem], imm64 is not.

Effective address — the one formula

[ base + index*scale + displacement ]

base   : any 64-bit register
index  : any 64-bit register except rsp
scale  : 1, 2, 4 or 8   (element size)
disp   : signed 32-bit constant

Every memory operand in x86-64 is some subset of that. Examples:

mov al,  [rsi]              ; *ptr
mov eax, [rsi + 4]          ; ptr[1] of int32
mov eax, [rsi + rcx*4]      ; arr[i], int32
mov rax, [rbp - 8]          ; a local variable
mov rax, [rel counter]      ; a global, RIP-relative

LEA does the arithmetic without touching memory: lea rax, [rsi + rcx*4] puts the address in rax. It is also the fastest way to compute rax = rsi + rcx*4 in general.

Widening and narrowing

Loading a small value into a big register is never a plain mov.

movzx eax, byte [buf]   ; unsigned byte -> 32-bit
movzx rax, word [buf]   ; unsigned word -> 64-bit
movsx rax, byte [buf]   ; signed   byte -> 64-bit
movsxd rax, eax         ; signed  dword -> 64-bit
mov   eax, eax           ; unsigned dword -> 64-bit (free)

Narrowing needs nothing — just use the smaller name: mov [buf], al.

Alignment: keep an N-byte value on an N-byte boundary. Misaligned works on x86 but costs cycles, and SSE movaps faults outright — that one needs 16.

Frames

The stack and how to size sub rsp, N

The stack grows downward. push subtracts 8 from rsp then writes; pop reads then adds 8. rsp always points at the last thing pushed — the lowest used address, not free space.

With a frame pointer, locals are addressed from rbp (stable) and outgoing arguments from rsp (moves). Optimised code drops rbp and indexes everything from rsp.

The three rules

1 · 16-byte alignment

rsp must be a multiple of 16 at the moment a call executes. The call then pushes 8 bytes of return address, so on entry to any function rsp % 16 == 8.

That gives the rule you actually use: after your prologue, rsp must be back to a multiple of 16. Break it and SSE code inside printf or malloc will segfault.

2 · Shadow space — Windows only

Before every call on Windows x64, the caller must reserve 32 bytes above the return address, even when the function takes no arguments. The callee owns that space and may spill rcx rdx r8 r9 into it.

This is the "always 32" rule. It does not exist on Linux or macOS.

3 · Red zone — System V only

A leaf function (one that calls nothing) may freely use the 128 bytes below rsp without reserving them. No sub rsp needed at all.

Not available on Windows, and not inside interrupt/signal handlers.

Calculate your prologue

    
    
    
  
    

  
    The parity rule behind the arithmetic: entry leaves rsp % 16 == 8, and each push removes another 8. So with an even number of pushes your N must be ≡ 8 (mod 16); with an odd number of pushes, N must be a multiple of 16. Counting push rbp, the everyday case "push rbp + locals" lands on a multiple of 16.
    

  
    Parameter homing — reading MSVC / MASM output
    
  
    A Windows compiler at /Od starts almost every function by storing its register arguments into the shadow space. Those stores come before sub rsp, and that ordering is what makes the offsets look inconsistent.
    

  
    
    
    
      
    What the caller left you
    
      
    At the first instruction of a function, before you touch rsp:
    

    rsp+32  [ home slot 4 ]  <- reserved for r9
rsp+24  [ home slot 3 ]  <- reserved for r8 
rsp+16  [ home slot 2 ]  <- reserved for rdx
rsp+8   [ home slot 1 ]  <- reserved for rcx
rsp+0   [ return address ]  <- rsp
    
      
    The 32 bytes belong to the caller's frame but are owned by the callee. Homing is the callee spilling its arguments into them so every parameter has a real address:
    

    mov DWORD PTR [rsp+24], r8d   ; arg 3
mov DWORD PTR [rsp+16], edx   ; arg 2
mov DWORD PTR [rsp+8],  ecx   ; arg 1
sub rsp, 56                    ; frame opens AFTER homing
    
      
    The stores must come first because +8/+16/+24 are only correct while rsp still holds its entry value. Optimised builds usually skip homing and keep arguments in registers.
    
    
    
    
    
      
    name$ = N is an offset from the post-sub rsp
    
      
    MASM writes num1$[rsp] to mean [rsp + num1$]. Subtract the frame size to see what each symbol really points at — for a function with sub rsp, 56:
    
      
    
        
    
          
    SymbolAfter sub−56Really is
    
          
            
    step1$ = 32rsp+32−24a local, inside the new frame
    
            
    num1$ = 64rsp+64+8home slot 1 (from ecx)
    
            
    num2$ = 72rsp+72+16home slot 2 (from edx)
    
            
    num3$ = 80rsp+80+24home slot 3 (from r8d)
    
              
        
    
      
    
      
    Anything ≥ the frame size is a parameter above the return address. Anything below it is a local. So mov eax, num2$[rsp] is just reading back the byte homed a moment earlier.
    
      
    Where that 56 comes from: 32 shadow space + a locals block of 16 + 8 for alignment. The int step1 inside that block is only 4 bytes (rsp+32 … rsp+35) — MSVC at /Od rounds the locals block up to 16, then adds 8 because with no pushes N must be ≡ 8 (mod 16). Don't read a frame size as a sum of variable sizes: it is minimum needed, rounded twice.
    
      
    Leaf functions get neither. A function that calls nothing emits no sub rsp, so its symbols stay small: num$ = 8 is home slot 1, unshifted. $LN3: is just an end-of-prologue label and generates no code.

    cmp rax, rbx computes rax - rbx and throws the result away. Read the jump that follows as a sentence about the first operand:
    

    cmp rax, rbx

    Freestanding — no libc
    

    section .data
    msg db "Hello, world", 10
    len equ $ - msg

section .text
    global _start
_start:
    mov rax, 1          ; write
    mov rdi, 1          ; fd = stdout
    lea rsi, [rel msg] ; buf
    mov rdx, len        ; count
    syscall

    mov rax, 60         ; exit
    xor edi, edi        ; status = 0
    syscall

; nasm -f elf64 a.asm && ld a.o -o a
    
    
    
    
    
      
    Linked against libc — a real frame
    

    section .text
    global main
    extern printf

main:
    push rbp            ; rsp%16: 8 -> 0
    mov  rbp, rsp
    sub  rsp, 16        ; locals, stays aligned

    mov  qword [rbp-8], 42

    lea  rdi, [rel fmt]
    mov  rsi, [rbp-8]
    xor  eax, eax       ; 0 vector args
    call printf wrt ..plt

    xor  eax, eax       ; return 0
    leave
    ret

section .rodata
    fmt db "value = %ld", 10, 0

; nasm -f elf64 a.asm && gcc a.o -o a -no-pie
